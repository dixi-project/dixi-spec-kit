# Module — Command-driven workflow

## Purpose

Connect commands, artifacts and verifications to implement the specification-driven development domain. B1 implements the CLI, safe filesystem, resources and structural validation in `src/dixi_spec_kit/`. B2a adds shared recipes and context preparation in `workflows.py`; execution through adapters and later operations remain pending.

## Responsibilities

| Part | Responsibility | Boundary |
|---|---|---|
| Local CLI | Install resources, diagnose, validate structure and plan updates. | No inference and no calls to AI/AWS. |
| Resources and contracts | Share templates, rules, identifiers and per-operation behavior. | Do not duplicate different rules for each agent entry point. |
| Eligible adapters | Expose the same core operations in each tool, load context and declare capabilities/controls. | Do not select an agent implicitly or assume compatibility without evaluating each adapter. |
| Stack profiles | Connect the tools and checks of the chosen language/framework to `make verify`. | Python as the kit's runtime does not impose Python on the project. |
| Policy sets | Declare guarantees and mechanisms according to the project's decisions. | Portable/Dixi direction accepted; operational mechanisms pending per ADR-101. |
| Validation and evidence | Deterministic checks and recording of results tied to the reviewed state. | Do not replace semantic evaluation or human approval. |

`plan` reuses the domain, architecture, contracts and threats capabilities; the direct entry points work on the same artifacts. `analyze`, `verify` and `review` distinguish coherence, execution of controls and review readiness. The CLI does not execute text generated by the agent.

The no-integration mode keeps templates, guides and local validators. Adapters do not own the specs and do not change their IDs. An integration lacking the required control cannot announce equivalent protection; it must declare the limitation and respect the gate.

## Contracts and risks

Consumes [command-contract.md](../../07-contracts/commands/command-contract.md) by blocks. The guided workflow feature covers coordination; [local-core](../../05-features/local-core/feature-spec.md) makes B1 concrete with its [contract](../../07-contracts/commands/local-core-contract.md), [threat model](../../13-security/local-core-threat-model.md) and CLI/distribution tests. Update and integrations will have their coverage before their blocks are implemented.

Main risks: writing outside the root, loss of local changes, malicious instructions in documents, false/stale evidence and gate bypass. The kit's own threat model and per-threat tests are required before building. The product's `threat-model` command does not replace that obligation during its development.
