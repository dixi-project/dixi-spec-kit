# Command reference

## Purpose

One page per DIXI operation: what it does, when to use it, what it reads and writes, where it stops and how to invoke it from Claude Code, Codex or an Agent Skills compatible agent.

Generated by `scripts/build-command-reference.py` from the packaged command text; do not edit by hand.

## Commands

- [`/dixi.discover`](discover.md) — Discover the product vision, actors, scope and open questions
- [`/dixi.specify`](specify.md) — Specify domain, module and feature with verifiable criteria
- [`/dixi.clarify`](clarify.md) — Resolve doubts in a spec with questions and record decisions and assumptions
- [`/dixi.domain`](domain.md) — Design domains, bounded contexts and ubiquitous language
- [`/dixi.architecture`](architecture.md) — Propose design and architecture decisions as ADRs
- [`/dixi.contract`](contract.md) — Define or change a contract and its impact on consumers
- [`/dixi.threat-model`](threat-model.md) — Model STRIDE threats with mitigations and planned tests
- [`/dixi.plan`](plan.md) — Plan contracts, decisions, risks and tests for a feature
- [`/dixi.constitution`](constitution.md) — Create or amend the project's principles (its constitution), versioned
- [`/dixi.checklist`](checklist.md) — Write requirement-quality checklists for a feature (unit tests for the spec)
- [`/dixi.converge`](converge.md) — Compare the code with the feature's specs and append traced convergence tasks
- [`/dixi.tasks`](tasks.md) — Split a plan into tasks with criteria, dependencies and risk level
- [`/dixi.build`](build.md) — Build a task test-first: red, green and verification
- [`/dixi.verify`](verify.md) — Run project verification and map criteria to tests
- [`/dixi.review`](review.md) — Prepare a risk-based human review of a change
- [`/dixi.analyze`](analyze.md) — Analyze spec chain consistency and the impact of a change
- [`/dixi.status`](status.md) — Show project status and a justified next step
- [`/dixi.handoff`](handoff.md) — Leave a local handoff to resume the work
- [`/dixi.change`](change.md) — Propose a change to a feature with its impact
- [`/dixi.data`](data.md) — Specify the data model, personal-data classification, retention and migrations
- [`/dixi.quality`](quality.md) — Define the test strategy, quality budgets and verification matrix
- [`/dixi.ai`](ai.md) — Design AI use cases, evaluation, data and agents under the project's provider policy
- [`/dixi.release`](release.md) — Prepare release readiness evidence, changelog proposal and rollback plan
- [`/dixi.promote`](promote.md) — Review the requirements to move MODE to prod and list missing evidence
- [`/dixi.operate`](operate.md) — Define SLOs, observability, runbooks and incident preparation
- [`/dixi.finops`](finops.md) — Estimate cloud and AI costs with explicit assumptions and budgets
- [`/dixi.compliance`](compliance.md) — Map compliance obligations and the evidence still missing
- [`/dixi.duediligence`](duediligence.md) — Produce a due-diligence report backed by project artifacts, with gaps
- [`/dixi.interview`](interview.md) — Fill the project's pending slots through a guided interview, one question at a time
- [`/dixi.risk-review`](risk-review.md) — Prepare a risk review report of a pull request, branch or diff for a person
- [`/dixi.onboard`](onboard.md) — Bring an existing codebase under DIXI: draft modules, features and traceability from the code
- [`/dixi.bugfix`](bugfix.md) — Fix a bug with traceability: reproduction, failing test first, minimal fix, spec updated
- [`/dixi.issues`](issues.md) — Turn a feature's tasks into GitHub issues with gh, after a preview the person confirms
